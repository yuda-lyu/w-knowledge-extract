# 累積經驗 — 經驗通則（w-knowledge-extract）

> **路徑基準**：原始碼在 `src/`，本檔所列檔案路徑除已標 `src/`、`test/`、`toolg/` 者外皆相對 `src/`；上游三套件（抓取 `w-knowledge-capture`、摘要 `w-knowledge-summarize`、關聯 `w-knowledge-relate`）之檔寫作「<套件名> 之 <路徑>」，位於 `node_modules/<套件名>/`。
> 本檔為與本套件相關之累積經驗通則（節號沿用原編號，未收錄之節為使用端或上游套件之運維經驗，缺號）。過程性教訓寫此，現況寫 `../state/state.md`。

## 1. AI 供應商目錄:設定與內建預設席位要跟著上游目錄走

設定（`ai.providerPick`、各席 `use`／`fallback`）引用內建目錄之條目 id，有兩種形狀會出問題：

| 形狀 | 後果 | 察覺方式 |
|---|---|---|
| `providerPick` 列了內建目錄**沒有**的 id | `resolveProviders` 回 missing → `createAiAdapter` 拋錯 → **整輪不執行任何階段** | 建構期即拋 |
| 名額（`use`／`fallback`）引用了**不在** `providerPick` 的 id | **靜默略過**，不拋錯；該席位遞補鏈默默變短甚至變空 | 不會報錯，只能靠啟動期席位檢核（`extractSeatsOf`、`extractSeatsProblem`）或人工比對 |

**多次發生，全是同一形狀**：上游把條目下架或改名，而設定（含**套件內建預設席位**）還留著舊 id。守則：

- 每次上游套件（`w-dispatch-ai`、抓取套件）升版後，逐一比對 `providerPick` 與內建目錄並列出差異；不要只看 `npm i` 成功。套件內建預設（`core/extractSettings.mjs` 之 `EXTRACT_AI_DEFAULT`／`EXTRACT_DEFAULT.ai`）亦同，由 `unit-settings` 等測試抓出。
- **限時免費條目視同易失物**：採用前先想好下架時的退路（誰承接、遞補鏈夠不夠長），並預期它隨時消失，壽命可以短到一天；套件預設席位用到限時免費條目時，須隨上游目錄維護。
- **同一家不要同時坐太多席**：一家倒下就空了數席（起草 3、審計、修訂）。排席位時看的不只是分數，還有**故障域**——一家死掉會空幾席、遞補後是否仍滿足換家原則。
- `w-dispatch-ai` 之額度視窗查詢（`getQuotaClaude`／`getQuotaCodex`／`getQuotaAntigravity`）可讓呼叫端直接讀剩餘量與重置時刻，不必靠每輪失敗去推斷額度用盡。

## 2. prompt 長度上限:安靜失敗、0ms、不計入逾時

`agy:`（antigravity CLI）**以命令列傳 prompt**，`w-dispatch-ai` 之 `dispatchAntigravity.mjs` 設 `MAX_PROMPT_LENGTH = 30000`（Windows 命令列上限扣掉 exe 路徑與旗標之保守值）。超過就**未執行即回失敗**（errorType `params`），耗時接近 0ms——不像逾時那樣顯眼，健康表上只是多一筆失敗，實際效果是「那個席位從來沒真的工作過」。

- 實測：關聯（6 篇 × 25 候選）之提示詞 4 萬餘字元，每輪全數 params 失敗、全由遞補席承接；候選數降到 15 後約 2.5 萬字元，主力可用。提煉整合提示詞長度 ＝ **各候選字元總和 ＋ 511**（單份候選約 3,700～6,400 字元），故**起草席位數直接決定整合輸入長度**。
- 兩條路徑對超限的處置不同：`callJson`（摘要／關聯／預篩）經抓取套件 `src/core/ai/capability.mjs` 之 `fitChain`，**呼叫前**依實際提示詞長度把放不下的條目剔除、直接改派遞補，不產生失敗紀錄；`getWkf`（提煉工作流）**不經** `fitChain`，超限時是 agy 回 `params` 後才遞補（未 spawn 故成本低，但會計入健康表）。
- **教訓**：註解裡的「約 1.5 萬字」實測低估三倍。**提示詞長度一律實測**，不要憑印象估；改動候選數、批量、席位數時都要回頭重量。

## 4. 提煉工作流:席位設計的幾條約束

- 現行為 3+3 差量工作流：三家獨立起草各出一份差量 → 整合（via 指回候選；程式計票以實際成交之供應商計、ref 閉包）→ 審計（只列問題）→ 修訂（只出補丁，補丁守門）→ 終審（逐操作裁決；不可逆操作須明列）→ 程式套用。補丁守門依操作類別映射：剔除建設性操作才受限，剔除破壞性操作＝保住既有知識，一律放行。
- 前段起草（`runFanout`）是**屏障**——等所有起草席全數結束才收斂，故**任一席逾時就拖慢整輪**，慢家的逾時要設短止損；後段審計 → 修訂 → 終審為串行角色鏈，初稿即整合的產出。
- **換家原則**：終審（accept）不可與修訂（revise）同家（自己審自己改的稿看不見自己的盲點）；審計與修訂同家則無妨。
- `budgetMs` 一律由程式自動推導（＝該鏈各條目逾時之總和），**不在設定裡手寫**。起草席位數改變時，它同時改變整合輸入長度。
- **整份重寫會把稿改壞，改用「差量＋程式守門」**：整份重寫時，修訂照審計之「離題／篇幅超限／假爭議」意見大段刪除，舊核心與新知一起流失。改為修訂／終審只輸出 edits／adds／removes，由程式套回並守四條不變式：①舊核心與本輪輸入稿之知識條目不可因改寫而流失；②刪除只准「重複」或「引用**高**嚴重度之離題／捏造意見」（中、低只能刪減該條）；③「假爭議」不是刪除理由（兩方須先移入他欄），舊核心爭議不可刪；④parameters 須為物件。判準：**審後不得比審前差**——這一段之價值是修錯，不是重寫。
- **審計之「離題」判定是新概念（無舊核心）品質之主要變異來源**：同一題兩次審計，一次把「全文未提及該概念」之筆記判離題、修訂照刪，另一次判較寬，定稿分數差二十分。規則表「整篇無關者不寫入」本身就容許此刪除，勿為拉高單題分數而放寬離題刪除。

## 16. 測試之 cwd 與「匯入即執行」

- **成因**：測試以 cwd 為掃描根，掃描範圍內有匯入即執行之腳本（CLI、一次性工具、發布腳本），逐檔 `import()` 即把它們跑起來。
- **修正與通則**：以測試檔位置推導根（規則帳本 GEN-09），且根必須是 `src/`。**會 import 或執行所掃到之檔案者，根一律取自模組位置；入口腳本之頂層副作用（頂層 await 跑管線、改版號、清資料夾）使「import 它」等於「執行它」。**
- 本套件實例：原始碼移入 `src/` 後套件根多了 `toolg/` 與 `g.mjs`，以套件根為根的 `unit-extract-entry` 一跑就把 `package.json` 版本加 1（見 `experience.md` 第 19 條）。
- **研判紀律**：發現異常（檔案被改、日誌異常）後先查行程命令列與 AI 用量檔，再以 `-newermt` 列出期間內被改之檔案，三者交叉即可在數分鐘內界定影響範圍，不需猜。

## 19. 檢定標準:判準要能在真實語料上逐條核對

- **比率判準會把違規藏起來**：正體原以「簡體比例 ≥2%」判，在真實語料上只量到極少數；改以**數量**（違規處數＝0）判，度量只作標準之定義並以逐案測試釘住兩側。
- **字典推導之「簡體專用字」須納入地區異體**：只用 opencc 之 ST／TS 表時「群、峰、床、秘」被判簡體（opencc 標準正體用羣、峯、牀、祕），大量誤判；加入 TWVariants／TWPhrases 之值後歸零。**任何字表推導都要拿真實語料跑一次、看前 N 名命中之上下文**，不是看單元案例過了就算。opencc 片語表不能當「誤用詞」表（其目標是 OpenCC 標準正體，大量臺灣合法用法會被判誤用）。
- **數字紮根之誤判幾乎都在「識別碼與格式」，不在數學**：以筆記雜湊稱呼對方、候選編號、全形逗號經 NFKC 變千分位、上標黏後數、年份簡寫、印度計數、時刻 3 PM、黏連數字、小數點開頭……**每修一類就重跑掃描再抽核，直到剩下的全是真違規**，每類寫成迴歸案例。
- **抽核要看實例上下文，不看計數**：初跑數百條違規，抽 10 條即見 8 條是雜湊；若直接把計數當違規數交處置，會撤掉數百條合格內容。**不合格須無誤判，邊界含糊者列「未能判定」。**
- **同秒碰撞是時刻比較之常見陷阱**：以「時刻 ≥ 版本即已判」排除，測試跑得快時與版本同一秒 → 間歇漏評。無法分先後即未能判定 → 照評（寧多評一次）。間歇失敗不放過，先連跑重現再查成因。
- **「後備值」會把上游壞掉藏起來**：要知道「被救回／被拒」各幾次，才看得到供應者壞了。
- **閘門上線，測試替身要先補成真實形狀**：失敗的案子全是替身之理由寫 'r'、'x'（去標點後不足字數），不是功能壞。順序：先寫閘之單元案例（各標準正反兩側），再全套跑，逐一把替身改成合標準之內容；不可為了讓舊案過而放寬閘。
- **改組提示詞之程式碼（抽函數、共用區塊）後，以評比題目識別（`planExtractBench(角色).promptFp`）驗逐字不變**——比肉眼比對可靠；識別一變，既有評比結果即全數失效。
- **AI 之「宣告」不算處置，以落地狀態之結構判**：衝突去向若以起草之 conflicts 宣告為準，模型只要寫「立爭議」就過關；改為檢查落地後兩端是否真的分屬爭議兩方／有取代／本版加了條件。宣告只用於分流，不用於放行；同理，AI 自報之「已涵蓋」「已修正」一律以產物複驗。
- **區分「設定換版」與「內容真變」要用與設定無關之雜湊**：內容鍵含章節設定，改設定就全部換版；另記只依正文（正規化空白）之雜湊 h，h 同 → 靜默換版、h 異 → 才重審；舊紀錄無 h 者不能推定，計 unverifiable 並以現值為基準。
- **削弱已審定之標準前先量**：「常是／多半」須附數量；放寬標準（少檢一類）比加嚴更需要證據——放寬的錯誤是靜默放進有問題的知識。
- **從截斷的輸出補寫識別碼＝捏造**：題組／夾具中的網址、id、檔名一律以程式自來源取值或逐字比對驗過，不靠目視補寫。
- **判定小組之替身須讓各席之「實際供應者」不同**：共用替身以角色名當供應者，兩個覆核席會被判同一供應者 → 永遠未成立；替身之判定小組角色改以席位條目為供應者。
- **提示詞範例會被照抄**：範例 `"kinds":[null,"rule"]` 只是示意某方不另立主張，模型卻在兩方皆須轉主張時照填 null。範例要對應最常見之真實形狀，特殊值用文字規則說明而不放進範例；程式端對照抄之值要明文擋下，不靠後備值。
- **新欄位別掛在會被整筆重寫之紀錄上**：加欄位前先 grep 該紀錄所有寫入點（`seen[筆記]` 在維護首見、換版、重設基準、pass 落帳 4 處整筆重寫，掛上去即被沖掉）；改為獨立欄位並另列不變式。
- **量進料再談開不開**（ES10）：夥伴進料可遠大於預設容量。開關預設停用，容量配置交使用者——不以截斷或過期丟棄夥伴（靜默縮減）。
- **判準本身含糊時，調措辭不會收斂**：三輪措辭此消彼長時換路——把可判定之部分收斂成封閉清單、判斷改為步驟式、模型仍偶發之偏差用程式強制。**模型自由度與標準不一致時，用程式收斂，不靠再補一句提示詞。**
- **待判要有「條件成立自動結案」的出口**：凡登錄待判（owner user），要寫明哪個可觀察條件成立時由管線自己結案，並有單元案例；交付前把「使用者照建議做完之後下一輪會怎樣」走一遍。
- **全量預演本身就是測試**：單元案例全綠，對真實全量預演才看到共用函數把「擠標籤＋計數尾碼並存」之標籤修成亂鍵。**改資料之工具，先對真實全量預演、看「改了什麼」之分布與異常，再談套用。**修正函數要以「修完再驗一次」測（任一不合格輸入 → 修正後為合格），不只測輸入→輸出一對。
- **修正要對準標準之「對象」**：設計修法前先確認該標準檢的是哪個集合、哪個欄位。
- **題組全過不等於端對端對**：題組只驗出過題的形狀；新標準上線前必以真實資料跑一批端對端，逐筆看去向，看到新形狀再回補題組（一般案＋未見過之保留題）。
- **一次送審之量要有上限**：專步原把本輪全部候選一次送審，配額設大就成單一超長提示詞；比照每頁 10 條，中止時已判之頁照樣處置。
- **保留題失敗先複核出題，不是改提示詞**；**補定義也會改變裁決邊界——改提示詞後必以題組重跑**；要模型做不同之事時，改指示之對象（那一項），不改全體共用之定義。
- **品質測試要走生產之分批**：「正式提示詞」包含組裝它的所有參數（預算、分批、材料截斷），不只模板；評比工具可刻意凍結（題目識別），驗收測試不行。
- **題組同一案兩次各判一邊＝案本身判不清，不是調提示詞之訊號**：兩邊理由都成立 → 案之問題；一邊明顯錯 → 提示詞或模型之問題。偶發不穩如實記錄重跑次數。
- **席位聽話不代表輸出合格，改寫理由一律再過閘**（模型把原理由之數字寫錯，被數字紮根閘擋下）。
- **無聲截斷看「上限處的突起」找得到**：修法為於上限內最後句讀處截並記錄，無句讀則全文保留（抓取套件 `src/core/util/text.mjs` 之 `cutAtBoundary`）。
- **測試注入之日誌字樣須與程式現行輸出逐字相同**：最好與產生端之單元測試斷言同一字串。
- **符合度掃描每輪跑之成本**：新增或改寫掃描之標準時，改後即量一次全量；「庫再大一倍時重量」之觸發條件只看資料量，漏了「掃描之實作／範圍改變」。
- **審查報告逐項回到改動處讀碼再接受**；**收尾盤查以逐格核實之表為據**，不以帳本條目存在推定「完成」。

## 29. 提煉套件之組裝與契約

- **替身測試抓不到上游之預算邏輯，真上游測試才抓得到**：提煉之 3+3 以替身測過數百案，接上抓取套件之調度層（工作流入口）＋假 REST 之第一案即「起草全敗」——席位逾時 5 秒而未給 `minAttemptMs`，上游以 20 秒為開工門檻、預算（逾時×鏈長）只有 5 秒，一次都不送出。**「間歇失敗」先懷疑邊界相等之比較**，不是重試。正式設定（逾時充足、席位明給）未觸發，故只改抓取套件之調度層。
- **日誌契約以三向驗證**：①原始碼之全部 WARN／ERROR 發出點（去註解、讀首參數之字面）逐一歸類，字樣在運算式內者（pass 名、截止之說法、逐棒前綴、CAS 之原因）自原始碼之常數推導樣本，不手抄；②真實執行之每一行警告回溯到某個已歸類之發出點；③report 鍵＝多條件路徑之實際 report 之聯集。突變（改字、新增未歸類之警告、漏列 pass 名、漏 report 鍵）皆轉紅。只靠②會漏掉沒跑到之路徑，只靠①會漏掉字樣在運算式內者。
- **跨套件契約要以對方之真實件產物驗**：以摘要套件之真實版型（全部選填章）產筆記，比對其章名集合與提煉之讀法——曾抓到「可驗證要點」不入起草之輸入；改之即改全部提示詞與內容鍵之版本，須先以正式席位 A/B，故釘住現況並列已知限制，不順手改。
- **兩側之「內容變更」不同層**：摘要之內容同步只看同步欄位（標題、一句話重點、概念…）之雜湊；提煉看全部內容章之內容鍵。摘要偵測得到者提煉亦偵測得到，反之不然——寫契約測試前先讀雙方之判定，不要假設同一口徑。

## 33. 四套件之界定:泛用開源套件之視角（規則帳本 GEN-20）

- **先寫界定再審，審的是「違反哪一條原則」而非「哪裡可以更好」**：否則審計會滑成無盡的改善清單。「刻意」與「違反」要分開列——刻意者只進 README 已知限制。
- **「字形標準不適用」要列為 NA、不能變 0**：正體標準於非繁體中文時若直接不判，掃描總量歸 0 與「全部合格」在報表上無法區分；逐件列不適用（受檢總量不變、違反 0、合格 0）才看得出是語言設定關掉的。不適用字樣只一份（抓取套件之 `SCRIPT_NA_DETAIL`）。
- **語言設定要在最底層解析一次、以物件傳遞，不在各處重解析字串**：`resolveLocale` 回凍結物件 `{ code, label, han, script, slug }`，runtime 解析後放 `deps.locale`，純函數經 `scriptOf(opt.locale)` 取字形政策（未給即預設正體）——既避免各呼叫點各自判語言，也讓測試能以字形政策物件直接注入。`Intl.getCanonicalLocales` 驗代碼、`Intl.DisplayNames` 取表外語言之稱呼，不手列全部語言。
