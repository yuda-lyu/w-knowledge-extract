## 套件審計與重整之心得

1. **行為在結構之前**：先修持久檔語意與先記後寫、兄弟段與閘，再搬檔與層序——搬檔時行為已定，差分才有意義。每步不搬檔、新件放最終落點之目錄。
2. **基礎設施失敗不是使用者之待判**：缺票、同一供應者、中止、席位未設一律留待（runPass 存待審、pending 留待審、專步退避），逐項計次只對「兩票可用而判不了」；否則額度問題會轉成使用者之待判山。
3. **閘只此一份**：`gateOps`／`opStandardsCtxOf`／`applyCtxOf`／`applyWithInvariants` 各一份，八處字面改取之；尾端寫入（涵蓋落帳、待審、排除集、證據）在不變式之前，被剔者逐條列明。
4. **`{"verdicts":[]}` 不是「全部 keep」**：一條有效裁決都沒有而有操作，等同終審失敗（整併整份不套、一般差量破壞性存待審）；測試替身之終審改用 `keepAll`（逐操作 keep），「漏裁決」之情境以只裁非終態者模擬。
5. **整合不得改變操作種類與目標**：測試造「以 add 之候選 via 出 essence」會被新規則拒收——起草者各出一份本質、整合指回之；同類測試之替身要與正式規則同形。
6. **素材雜湊要分「含內容鍵」與「只結構」**：ES14 之 `doubtChecks` 記 `hash`（含出處內容鍵；專步與掃描比之）與 `shape`（渲染不讀內容鍵比之），否則渲染永遠判未覆核或內容變了判已覆核。
7. **豁免不重登之路徑多被檢核紀錄先擋住**：同義對之「已豁免且素材未變」在紀錄仍有效時到不了（紀錄先判不需檢）；只在紀錄失效（標準改版）而素材未變時生效——測試要造紀錄失效才驗得到。
8. **統計鍵要守門**：`count()` 之鍵不在初值表即被靜默吞掉——改為 WARN 一次（須見）；report 之鍵全集與實際 report 之聯集由契約測試釘住。
9. **區域小件先查抓取埠**：新寫之共用處先查 `core/capturePackage` 之 `strOf`／`textValueOf`／`strictTextOf`，不再寫區域 `str`（逐字同之跨檔同名由 `unit-extract-package` ⑦ 守）。
10. **搬移 0 差要先凍結名集**：`export *` 兩模組同名即靜默剔除該名——拆檔前取入口具名匯出名集凍結入測試（438 名），改名以 `RENAMED_SINCE_SPLIT` 對照；為避撞名而生之新名寧可內聯也不出入口。
11. **葉模型下共用件之家**：葉（domain／bench）可取全部，各層不得取葉——分身轉址頁之內建版型因此落 `stores/coreProjection`（domain 轉出並作預設）、`SUPPORT_KINDS` 落 `standards/supportCheck`（domain 轉出）、`LEAK_PHRASES` 落 `coreStandards`（opGuards 轉出），否則成環或逆向。
12. **小件收斂之 0 差判準**：`str` 34 份皆逐字同 `textValueOf`，不確定是否只收字串者一律 `textValueOf`（不升級為 `strictTextOf`）；語意異者（`conflictDisposition` 之 `strs` 非陣列回 `[]`）改名不收斂；`oneLine` 與抓取 `oneline` 之截斷字樣不同亦不收。提示詞由常數產生者以 golden 不重產而綠為證。
13. **詞彙之 null**：共用 `mergeGuideFields` 以 `given()` 判未給，null 恆取預設——「null 改空字串」與程式事實不符；自訂型別只為保一行測試字樣即違反一規則一份，改回共用 `'estr'`。
14. **describe 定義期不可以未初始化之路徑建庫**：`let TMP = ''` 改在 `before` 內賦值後，留在 describe 層之 `mkEnvIn(TMP)` 以空字串建出磁碟根下的目錄（測試夾具數百檔）。守則：以 TMP 建構之 env 一律延後到 `before`／首次呼叫；`mkEnvIn` 拒非絕對路徑；磁碟根之刪除屬不可逆，須使用者同意。
15. **新加之斷言先單跑再入全套**：修程式後之對應測試一律先單檔跑綠，再跑全套（曾因斷言字串與實際不符，全套白跑一輪）。
16. **新不變式要對存量與合法路徑免責**：「爭議之不同方引同一主張」若無條件報，爭議併爭議（各方原樣併入）之既有案即紅；改為只報「方數未變而新產生者」並以存量盤點 0 違反後才入 `checkInvariants`。拒收放在 merge 之前（`coreDelta`），不變式只是後盾。
17. **提示詞之契約缺口只有正式席位實跑才看得到**：`wf-pending` 題組以應然回覆全綠、golden 逐字同，實跑 sonnet 卻 9/16——失敗者恰為全部「留待審」案，因提示詞只說「不可逆須逐條明列裁決」而無「材料不足則不列」之路，與正式待審機制相悖。處置：待審模式加一句、同席同題組 A/B（15/16、無回歸）即採用並寫回退判準＝換席；唯一未過者為可爭議案，不為單一邊界案再調提示詞。改提示詞之步驟：改 `buildReviewPrompt` → `regen-golden.mjs` 預演（覆寫組須先手改同句，否則比對中止）→ `GOLDEN_WRITE=1` → 相關測試 → 正式席位實跑。
18. **評分之頁組法與正式同一會使題組指紋失效**：ES9 題組改頁內重起＋出處去重後，須以正式席位逐案兩次重驗；只換指紋公式（`benchPromptFpOf`）而提示詞未變者不重驗。
19. **根目錄改結構後，以套件根為掃描根的測試會「匯入即執行」發布腳本**（2026-11-02 重整為 `src/` 佈局時發生）：`unit-extract-entry` 原以套件根逐檔 `import()`，原始碼移入 `src/` 後套件根多了 `toolg/`（`addVersion` 改版號、`cleanFolder` 清 `dist`／`docs`、`modifyReadme`）與 `g.mjs`，一跑測試就把 `package.json` 之版本加 1。守則：掃描與逐檔載入之根一律是 `src/`（GEN-09）；測試跑完後以 `git diff -- package.json` 確認未被改動。
20. **範例與 JSDoc 之 `// =>` 要實跑**：補寫 `@example` 時以腳本實跑取輸出（含 `need test in nodejs.` 者除外），曾見既有範例之預期值與實跑不符（`selectNotes` 之排序、`extractResolvedProblem` 之截斷字數）；補寫之範例亦曾落入領域詞（被 `unit-extract-package` ⑤ 抓到）——範例題材一律用中立題材。
21. **題組的預設值若與正式規則衝突，評分失真卻靜默**（2026-11-06，使用端 Gitea #87）：八個 `wf-*` 角色之題組都沒給 `input.state.concept`，`coreStateOf` 預設「題組」；正式提示詞規則 1 要求離題者列入 skipped，模型把與「題組」無關之合成材料全判離題（對題組是正確反應，錯在題組）。使用端只在起草、審計兩角色看到 1～4/16 的低分，實際範圍是八個角色（以 `planExtractBench` 逐角色數「題組」字樣出現頁數即可一眼看出：16/16）。守則：①報缺陷時不以使用端回報之角色數為範圍，用指令盤點全部角色；②這類「題組與正式規則互相衝突」要在準備期守門（`wfConceptProblems`），不能等付費跑完才以低分現形；③守門掛八角色共用之 `wfInputProblems`，不掛各角色之 `inputProblems`（後者在共通檢核有問題時不執行）。
22. **概念名過窄會把乾淨操作判成離題**：訂概念名要逐案核對「乾淨／應收之材料」是否都在概念內——例如乾淨操作談「月圓前後暗星較難辨識」（月相）而概念取「觀星地點選擇」、談「團體過大時後排聽不清楚」而概念取「導覽解說節奏」、談「頻繁掀蓋」而概念取「燉肉火候」，模型都可能依規則 1 判離題（高）；寧取較寬之上位概念。反向案（意見或撤回理由主張「離題」而 `why` 載明不成立者，如終審 c09／ch2、待審 p10／ph4）概念名必須涵蓋被指離題之材料。概念名之實效無法以程式判定，只能由正式席位重跑評比驗證。
23. **批次改 JSON 題組用文字層插入並以深比對自證**：題組檔排版（單行陣列、混合縮排）人工維護，`JSON.stringify` 重寫會整檔改版；改以逐案行插入（無 `state`／單行 `state`／多行 `state` 三種形狀），寫入前以「除新增鍵外與 `git show HEAD:<檔>` 之原檔深比對相同」自證，再附 `git diff --stat`。

24. **入 seen 之守門只管入 seen 當下，日後回歸要有「維護回頭檢查」**（2026-11-06，使用端 Gitea #88）：ES5 在 `settleConflictDispositions` 判「已處置才入 seenConflicts」，但處置結構日後可被拿掉——依衝突所立之爭議被 `dispute_dissolve` 拆解（起草、整併、爭議覆核三處落地，來源是正式流程之常態：終審存疑後起草拆解）、「加條件之修正」所依之主張被撤回或取代（`conflictDisposedOf` ③ 不計終態主張）。邊留在 seen：不再呈現、不交 RS4，掃描判違反、舊制只能人工存量處置。守則：①「入口守門」類標準要同時問「日後回歸誰處置」，不為各落地點逐一補處理（來源路徑會增加），改在維護以同一判定每輪回頭檢查；②判定與掃描、存量處置共用 `es5RowsOf`，只取無處置結構者（`es5ReopenOf`），不另寫一份；③移出後之收尾不另寫，走既有之重審項 conflict → 起草處置／宣告非對立交 RS4／逾 2 次交 RS4，有界——交 RS4 後 `rs4Held` 命中即不再移出，測試要跑到交 RS4 後再維護一輪證明不循環；④待判登錄以任一狀態計（未結、已結案、已豁免皆算已交），與 `es5CtxOf` 同讀；⑤`stageExtract` 入口已檢 `stores.holds` 必開，「待判集合未讀入」之分支階段層造不出，守門集中在純函數（非 Set 即不處置）並以變異證明，不為不可達之分支在階段內另寫三元；⑥取代（②）處置本身為終態、不會消失，會消失者是①爭議與③加條件之修正所依之主張——測試形狀要對得上，造「取代」案要用「被修正之主張被取代」；⑦步驟標號：維護內 ③‴ 已為隔離之解除，新步驟稱 ③′之二，不沿用提案之標號。
25. **造「處置結構消失」之測試形狀**：段內三輪（首批立爭議或加條件主張 → 次批以新筆記入批並拆解／撤回／取代 → 第三輪維護），新筆記須被該次起草涵蓋（否則第三輪另有一般批、`recheckPasses` 與 AI 次數對不上）；關聯邊之兩端須各被其他主張引用（否則主張終態後兩端不再被引用，無重審項、不重呈）；邊須帶 `createdAt`／`updatedAt`（重審項依邊時刻判到期）；僅重審 pass 之起草替身一律全略過並記提示詞，斷言每個起草席之提示詞皆有 `- R1` 列（三席各叫一次）。改狀態檔之案（首見基準、類別層）以 `fs.writeFileSync` 改狀態與 `cores.replace` 改記錄之 scope。

26. **評分謂詞自抄一份正式規則，日後必漂移；改抽共用判定件，並以交叉測試與舊式凍結守**（2026-11-06，使用端 Gitea #89）：審計謂詞要求植入之「重複」須高嚴重度，正式移除判準（`removalAllowed`）對重複不論嚴重度、審計提示詞之「高」不含重複——模型照提示詞標中反被判失分。守則：①評分端要重現正式判準時，從正式模組匯出判定件（`removalIssueOf`），不抄；使用端建議檔附之「另寫一個 `auditFlagged`」草案雖可用，仍是第二份規則；②抽出共用件前先劃**邊界**：只抽「意見面」（類型×嚴重度×指向），破壞性放行（需操作類別與狀態）、爭議類移除理由與終審自述之 reason（需移除方之理由）留在原函數——若把爭議類的「重複不足」放進共用件，會改變「爭議類＋離題理由＋重複意見 → 放行」之既有行為；③「既有行為不得改變」以**抽出前之逐字舊式**寫進測試做對照，全積（操作類別×類型×嚴重度×指向×自述理由）逐格同，不抽樣；④「兩邊一致」以全積交叉驗（`removalAllowed` ↔ 謂詞），並做三種變異看咬不咬：改共用件（兩側同變，交叉格仍一致，由明確期望值案抓）、只改一側（交叉格紅）、評分端改回舊邏輯（紅）；⑤謂詞放寬一邊（重複）後，對稱的另一邊（`clean` 只計高嚴重度，標中重複於乾淨之操作而正式流程可據以移除）要列為待裁示，不默默放過。
27. **題組材料與應然是否一致是語意判斷，能機械守的另立帳**：乾淨之操作之利／弊「不寫出處所無之內容」無法程式判定，改為把每條非「出處未載」之標注列成帳（案、操作、欄、標注、出處原文片段），測試只核：未列於帳者失敗、帳內片段須確在該案出處；增列標注者被迫人工核對並入帳。反證要對檢核函數本身（對舊材料的複本應檢出問題），不能只斷言「帳裡沒有」。另：有既有主張的審計案須附本質（否則 `stateDigest` 載「本批須以 essence 綜合現有主張」，審計列遺漏屬正確）；`kinds` 預期須與材料一致（單一案例之觀察不預期 `rule`、爭議之一方之依據不預期獨立 `pitfall`）。
28. **新增測試檔須同步 README §17 測試表**：`unit-extract-package` ⑧ 雙向對帳（漏列與多列皆紅），新增 `test/*.test.mjs` 後第一次全套即紅在這裡，與改動本身無關——寫完測試檔就先補表。
29. **mocha 單檔跑時匯出尚不存在的具名匯入會使整檔連結失敗**：修前紅要「每案各紅各的」，新匯出之件改以命名空間匯入（`import * as NS`）、案內取用，才不致整檔因 SyntaxError 一次全紅而看不出各案紅的原因。

30. **提示詞寫語意、程式比字面，語意正確之回覆就被拒收；越照範例做越失分**（2026-11-06，使用端 Gitea #90）：①`dispute_add`——提示詞寫「每方須有本批出處或所引既有主張」，範例一方只有 `claims`，納入閘卻要求**整條**至少一個本批出處（頂層 `sources` ∪ 各方 `sources`），各方只引同一差量之新主張 `@名` 者整條被拒（「無本批出處」）；②`param_add`——ES13 以字面判讀 conditions 是否含 `selfLimitPhrases`／`weakEvidence`（字串包含），提示詞只在規則段以一句帶過，模型寫「單一館之觀察」之類同義說法即不採。三個席位同形可重現，不是單一模型之能力。守則：①評比或正式日誌出現「同形、跨席位、越照提示詞做越失分」之拒收，先查程式之判讀是字面還是語意——是字面就把字面寫進提示詞，不是調模型；②寫進提示詞之字面清單由詞彙組出（與程式判讀同一來源）並以交叉案釘住（所列逐項經 `weakEvidenceProblem` 放行、同義改寫不放行），不在提示詞裡寫死第二份；③不改納入閘：兩處之要求（爭議須能回溯本批、ES13 字面判讀）合理，缺的是告知模型；④提示詞改動須先以正式席位 A/B（使用端已做：10/16 → 14/16），本套件側只落地並重產基準；⑤覆寫重現組不可重產——順序為先就地置換該組受影響之行並登錄手改紀錄，再跑 `regen-golden`（覆寫組比對過、中立組只列受影響之 2 檔）；⑥改提示詞後以全角色 `planExtractBench` 指紋前後對照（HEAD 解到 `./tmp/`）證明只有目標角色變；⑦順手盤點其餘「程式比字面而提示詞未寫」之站點記入規則帳本（`rulebook_prompt.md`），盤點可交子代理但其結論須主責抽核（本輪抽核之 6 項〔表中標「已核」者〕文字皆屬實，餘標「待核」）。

30. **相等比對遇空值，先問兩邊是否都可能為空；放寬一側之謂詞，對稱側要同步**（2026-11-06，使用端 Gitea #89 之續輪）：`issueOnOp` 以 `x.ref === str(op.id)` 比對，審計意見缺 `ref` 時 `normalizeIssues` 給 `''`，無 `id` 之操作的 `str(undefined)` 亦為 `''`，兩邊相等——缺 `ref` 之意見指向一切無 `id`／`ref` 之操作（多數新增主張），開啟修訂移除與終審剔除之閘。守則：①正規化把缺值變成 `''` 時，下游相等比對須先排除空；②判「可達」要沿正式路徑逐站查（`checkAudit` 不驗各意見 → `normalizeIssues` → `runPass` 直入 `issues` → 操作帶 `_oid` 而多無 `id`／`ref`），並以 `runPass` 端到端案證之（修前紅 `0 !== 1`＝缺 `ref` 之意見真的使 `add` 被移除）；③共用判定件一修，評分與正式同時生效，報告須標「正式行為之變更」；④`flags` 放寬為「足以使正式流程移除」後，`clean` 若仍只計高嚴重度，乾淨之操作被標中重複（正式流程會移除它）不被抓——對稱側同輪處理，兩條件取聯集（不是取代）。

## 通用之坑

- 套件測試一律自套件根跑（`npm test`），不自他處以 mocha 直跑單檔（暫存根與掃描根皆以測試檔位置推導，GEN-09）。
- 工具（演練、往返、評分）之輸出路徑要用絕對路徑，相對路徑會落到各自 cwd 下。
- 以免費模型跑評分時逐批即存、限流即停（限流字樣取抓取套件之判定，不自寫）；額度與同一供應者之其他席位共用。
